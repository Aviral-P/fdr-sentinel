# FDR Sentinel — 48-hour build plan

## Scope and approach

Build a local-only vertical slice first: an institution user creates an FDR, submits it with evidence, a scrutiny officer reviews it and requests clarification or recommends a decision, and an authorized approver records the final decision. Enforce role and institution scope on the API and audit each consequential action. Add extraction and integrity indicators as explainable human-review aids. Use synthetic demo records. Keep the stack to the specified React/Vite frontend and FastAPI/SQLAlchemy backend with PostgreSQL, or SQLite temporarily when PostgreSQL is unavailable. No deployment or external services are planned.

This plan was drafted before implementation began. The application source, backend migrations and tests, frontend, and local setup documentation now exist in the repository. The modules below describe intended milestone scope; the audit snapshot after the table records what is implemented and what remains incomplete. At each further milestone, inspect relevant files, state the plan, dependencies, risks and acceptance criteria before implementation; after implementation run the listed checks, fix failures, and report actual commands and outcomes before starting an unrelated milestone.

## Minimum first end-to-end data model

Start with these entities and add optional features only as the workflow needs them:

- **Institution** — stable ID, name, code and status.
- **User** — stable ID, name/login, password hash, role, active status and optional institution association (required for institution users).
- **FDRInstrument** — institution ID, declared instrument number, issuer/bank name, amount, issue date, validity/maturity date, status, submitted-by and timestamps. Keep extracted fields separate (either JSON with explicit provenance or a small related extraction record); do not replace declared values.
- **WorkflowEvent** — instrument ID, actor ID, action/from-status/to-status, comment and timestamp; supports the initial history and audit trail. If audit requirements outgrow this, split immutable AuditEvent from workflow history without changing API semantics.
- **Document** — instrument ID, original storage key/name, content type, size, checksum, uploader and upload time; extracted text/fields and extraction status/method remain derived data, never overwrite the original.

An initial SQLite database is acceptable for quickest setup; preserve PostgreSQL compatibility in types, migrations and queries. Keep file storage local and outside source control.

## Minimum API for the first working workflow

Use versioned REST/JSON paths (for example `/api/v1`), Pydantic request/response models, and derive identity/role from authentication rather than trusting client-supplied actor IDs.

- `POST /api/v1/auth/login` — authenticate and issue a session/token.
- `GET /api/v1/auth/me` — current user and role/institution context.
- `GET /api/v1/institutions/{institution_id}` — institution detail subject to scope; institution creation may be seed-only for the prototype.
- `POST /api/v1/fdrs` — create draft for an authorized institution.
- `GET /api/v1/fdrs` and `GET /api/v1/fdrs/{fdr_id}` — scoped list/detail.
- `PATCH /api/v1/fdrs/{fdr_id}` — edit allowed fields only while draft or clarification is open.
- `POST /api/v1/fdrs/{fdr_id}/documents` and `GET /api/v1/documents/{document_id}` — upload and authorized retrieval of immutable original evidence.
- `POST /api/v1/fdrs/{fdr_id}/submit` — submit draft for scrutiny.
- `POST /api/v1/fdrs/{fdr_id}/scrutiny` — scrutiny officer records review and either requests clarification or recommends a decision; must not itself approve/release.
- `POST /api/v1/fdrs/{fdr_id}/clarifications/{event_id}/respond` — institution response, then return to scrutiny.
- `POST /api/v1/fdrs/{fdr_id}/decision` — authorized approver records approve/reject and rationale; explicit human action required.
- `GET /api/v1/fdrs/{fdr_id}/history` — scoped workflow/audit timeline.

Every endpoint that accepts an FDR or document ID must independently enforce role permissions and institution-level data isolation. Approval is a recorded decision only; this prototype does not transfer or release funds.

## 48-hour prioritization

Complete milestones 1–5 as the first dependable vertical slice. Then add basic PDF upload/extraction and explainable deterministic integrity rules (6–7), followed by minimal queue/dashboard endpoints (8). Integrate the critical workflow screens (9), reserve time for fresh-start verification and synthetic demo walkthrough (10). Defer OCR for scanned files, polished analytics, elaborate exports and any optional infrastructure if they threaten the end-to-end workflow or testable authorization.
